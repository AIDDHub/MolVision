# 分子结构浏览软件 · 可行性分析

> 参考库：`COSMol-viewer`（Rust 渲染内核 + Python/WASM 绑定，解析由 COSMolKit 提供）
> 目标：导入 CSV / SDF / PDB 等常见格式，浏览小分子与蛋白结构。
> 约束：桌面版；Windows / Linux / macOS；完全离线；单文件分发；CSV 导入弹窗选列。
> **决策（已定）**：采用 **Electron + COSMol WASM**；放弃 PySide6 + RDKit + PyOpenGL，
> Rust 原生仅保留为备选（不再推进）。
> **决策更新**：保留 COSMol 3D，通过“相机 API 补丁 + 2D 标注画布”增强标签/测距；
> 2D 用 RDKit WASM；批量出图走“3D 截图 + 标注合成”。见 §14。

## 0. 产品定位（建议）

**一句话：面向科研与教学的轻量级分子/蛋白结构查看与出图工具——打开常见结构文件，
交互查看，调整样式，导出可直接用于论文/汇报的高分辨率图片。**

### 0.1 定位边界

| 是 | 不是 |
| --- | --- |
| 结构文件查看器（SDF/PDB/mmCIF/CSV） | 建模/编辑软件（加氢、修复、对接、MD） |
| 样式调整 + 高质量 PNG 出图 | PyMOL/ChimeraX 的替代（无光线追踪、脚本系统、高级分析） |
| 批量出图（SDF 多记录 → 每分子一张） | 数据库/协作/云平台 |
| 教学演示、组会配图 | 电子结构计算、性质预测 |

### 0.2 核心场景

1. **快速核对**：打开文件，确认分子/蛋白、配体、链、残基是否符合预期。
2. **论文/汇报配图**：统一风格、白底/透明底、高分辨率、固定视角。
3. **批量出图**：一个多记录 SDF → 每分子一张 PNG，打包 ZIP。
4. **教学演示**：切换球棍/卡通、旋转展示。

### 0.3 “出图”具体指什么

| 类型 | MVP | 说明 |
| --- | --- | --- |
| 3D 结构 PNG | ✅ | 当前视角，1×–4K，白/深/透明底 |
| 批量 PNG | ✅ | 多记录 SDF / 多选结构，ZIP 下载 |
| 2D 结构式 | 可选 | CK 的 2D 坐标 + `coordinates2d()` 可做基础版；高质量 2D 需 RDKit WASM |
| 3D 矢量（SVG/PDF） | ❌ | 3D 场景矢量化不现实；2D 可另做 SVG |
| 光线追踪/封面级 | ❌ | COSMol 是实时渲染，质量满足常规配图，不承诺封面级 |
| 标签/测量/多面板 | 二期 | 出图常用，但工作量大，建议二期 |

### 0.4 对方案的影响

- 增加 **导出对话框**：分辨率预设（1920×1080 / 2560×1440 / 3840×2160 / 自定义）、
  背景（深/白/透明）、样式、文件名规则。
- 高分辨率实现：渲染前把 canvas 尺寸设为目标分辨率，再 `takeScreenshot()`；
  受浏览器最大画布/显存限制，建议上限 4K–8K。
- 批量出图：逐条建 Scene → 渲染 → 截图 → JSZip 打包下载；需要进度条与取消。
- 透明背景需验证 WASM 截图的 alpha 通道；不行则用 Chroma 抠图或改离屏渲染。
- 2D 结构式若为硬需求，需加 RDKit WASM（`@rdkit/rdkit`），与“放弃 RDKit”冲突，
  需要单独确认。

## 1. 结论

**技术可行，且不需要修改 COSMol Viewer 的渲染内核。** 它已经解决最难的 3D 渲染
（球棍、棍状、蛋白卡通、表面、截图），但它是“渲染库/引擎”，不是完整应用：
CSV 解析、文件管理、结构列表、配体/核酸回退、错误处理都需要在它之上加一层薄应用。

需求已明确为：

- **桌面版**（不是浏览器里打开一个页面）
- CSV 导入时**弹窗让用户选择 SMILES 列**
- **Windows / Linux / macOS**
- **完全离线**
- **单文件分发**

在这组约束下，**最终选择 Electron + COSMol WASM**：

- Electron 自带 Chromium，三平台渲染行为一致，WebGL2 不依赖系统 GPU 驱动；
- HTML/JS/WASM/示例全部打进安装包，运行期**零网络请求**；
- electron-builder 可产出 Windows portable `.exe`、Linux `AppImage`、macOS `.dmg`，
  每个平台都是**一个下载文件**；
- CSV 列映射用普通前端模态框实现，交互最灵活。

代价：安装包约 **120–180 MB**（Electron 运行时 + 约 30 MB WASM），内存占用高于原生；
macOS 分发需要签名/公证，否则 Gatekeeper 会提示“未验证开发者”。

已评估但**未采用**的备选（保留备查）：

- **Tauri**：约 40–60 MB，但 Linux 依赖系统 WebKitGTK、Windows 需要 WebView2，
  难以严格满足“单文件、零依赖”；WebGL2 兼容性需逐平台验证。
- **Rust 原生 R1/R2**：R1 双窗口 6–9 人日；R2 单窗口 10–14 人日（需一行可见性补丁）。
  详见 §11。
- **PySide6 + RDKit + PyOpenGL**：小分子 5–7 周；含蛋白卡通 10–14 周；包体 150–300 MB。
  详见 §12。

最终 MVP 预计 **13–16 人日**；现有 `webapp/` 渲染层原型可复用，实际约 **10–13 人日**。

## 2. 参考库评估

### 2.1 架构

| 层 | 内容 |
| --- | --- |
| 渲染内核 | `crates/core`：Rust + `glow`/OpenGL，egui 原生窗口，离屏 PNG；卡通、球棍、表面、选择、动画 |
| 原生窗口 | `NativeGuiViewer` 通过子进程 + IPC 隔离渲染，窗口独立于宿主程序 |
| Python | PyO3：`cosmol_viewer`（渲染）+ `cosmolkit`（解析/化学） |
| Web | wasm-bindgen：`@cosmol-studio/cosmol-viewer` + `@cosmol-studio/cosmolkit` |
| 解析 | **COSMolKit**：SDF/MOL、MOL2、XYZ、SMILES、PDB、mmCIF；2D/3D 坐标、构象生成 |

版本：源码 `0.6.3-rc.1`；PyPI/npm 稳定包 `0.6.2`；MIT 许可。

### 2.2 已具备的能力

- 小分子：BallAndStick、Stick、Sphere，元素配色、描边、透明度
- 蛋白：Cartoon（ChimeraX 风格）、彩虹残基着色、原子/侧链选择、表面
- 交互：旋转/缩放/平移、相机参数、FPS、截图、动画播放
- 三端 API 基本一致：Rust / Python / JavaScript

### 2.3 明显缺口（应用层要补）

| 缺口 | 影响 | 处理 |
| --- | --- | --- |
| 没有 CSV 解析 | 需求明确要求 CSV | 自研适配层（两种 schema，见 §3.4） |
| 没有文件浏览/结构列表 UI | 不能直接当“软件”用 | 自研前端/桌面 UI |
| 多记录 SDF 需自行拆分 | 一个 SDF 可能含成百上千分子 | 按 `$$$$` 拆分，逐条建条目 |
| `Protein` 投影不含 HETATM | PDB 里的配体/离子看不到 | 单独提取 HETATM → `Molecule` |
| 没有核酸卡通 | DNA/RNA 只能球棍 | `BioStructure.toMolecule()` 回退，或后续自研 |
| 原生窗口不可嵌入 | Python 方案只能双窗口 | 选 Web/WASM 或接受双窗口 |
| 原生窗口依赖 OpenGL | 驱动异常时打不开 | Web 走浏览器 WebGL2，规避该问题 |
| 0.6.x 仍是 rc | API 可能变动 | 锁定 0.6.2，封装适配层 |

## 3. 格式可行性（已实测）

测试环境：Linux + Python 3.12 + `cosmol-viewer/cosmolkit 0.6.2`；离屏渲染使用
EGL/llvmpipe 软件渲染。数据仅为量级参考，GPU 上会更快。

| 格式 | 用法 | 实测结果 | 注意点 |
| --- | --- | --- | --- |
| SDF 单条 | `Molecule.from_sdf` | 6FI1 配体 12 原子，渲染成功 | 需要 3D 坐标；无坐标时球棍退化 |
| SDF 多条 | 按 `$$$$` 拆分后逐条 `from_sdf` | 2 条记录均解析成功 | 末尾多余 `$$$$` 会产生空记录，需过滤 |
| PDB（蛋白） | `Protein.from_pdb` | 1CRN 327 原子；1M17 2,511 原子 | 只含 ATOM，不含 HETATM |
| PDB（全结构） | `BioStructure.from_pdb` | 1M17 共 2,560 原子 | 用于配体/水/核酸 |
| PDB（配体） | 提取 HETATM → `Molecule.from_pdb` | 1M17 原始 49 条 HETATM → 49 原子/31 键 | 需过滤 HOH/WAT；离子也会混入 |
| mmCIF | `Protein.from_mmcif` | 6FI1 865 原子、2 条链 | 与 PDB 路径一致 |
| 核酸 | `BioStructure.toMolecule()` | 1BNA 566 原子/544 键 | 无卡通，只能球棍；`Protein` 为 0 原子 |
| CSV · SMILES | `from_smiles` + `embed_3d_conformer_` | 阿司匹林 13 原子；嵌入 0.02 s、渲染 0.25 s | 电荷/特殊价态可能嵌入失败，需逐行容错 |
| CSV · 坐标 | 生成 MOL V2000 → `from_sdf` | 水分子 4 原子；苯 12 原子 | 键需按共价半径推断，仅适合小分子 |
| 大蛋白 | 1AON 卡通 | 58,674 原子：解析 0.04 s、建场景 0.26 s、渲染 0.55 s | 软件渲染数据；内存占用需实测 |
| Web/WASM | 预编译 npm 包 | 无头 Chromium（WebGL2）渲染 12 原子成功 | 首次加载约 30 MB WASM（7.7 + 22 MB，未压缩） |

### 3.1 SDF

- 单条解析稳定；V2000/V3000 均可。
- 多记录：`MoleculeBatch.from_sdf_records` 对格式较敏感（尾部 `$$$$` 会报空块），
  **自己按 `$$$$` 拆分更可控**，还能逐条容错。
- 属性字段（`> <...>`）可按需读取，用于显示名称/分子式/分子量。

### 3.2 PDB / mmCIF

- 蛋白卡通渲染质量好，1CRN、6FI1 均正常。
- `Protein` 是“蛋白投影”，**不含 HETATM**。PDB 里的配体必须：
  1. 从原始文本筛 `HETATM`（排除水），拼成 mini-PDB，再用 `Molecule.from_pdb`；或
  2. 用 `BioStructure` 的 CID 选择按链/残基取配体（更复杂，需验证）。
- 核酸没有卡通表示；建议先回退球棍，并在 UI 标注“暂无核酸卡通”。
- 多模型 PDB（NMR）只显示第一个模型（`numModels > 1` 时提示用户）。

### 3.3 大结构性能

1AON（58,674 原子）在软件渲染下解析 0.04 s、建场景 0.26 s、渲染 0.55 s，说明
Rust 内核的性能余量很大。真正瓶颈会是 **WASM 内存** 和 **浏览器下载体积**，而不是
几何计算。10 万原子级复合物建议提供“原生/Python 模式”或分块加载。

### 3.4 CSV 设计（关键）

CSV 不是分子标准格式，必须先定义语义。建议支持两种，自动识别表头：

**A. 化合物表（最常见，优先）**

```csv
name,smiles
Aspirin,CC(=O)Oc1ccccc1C(=O)O
Caffeine,CN1C=NC2=C1C(=O)N(C(=O)N2C)C
```

- 必需列：`smiles`（兼容 `canonical_smiles`、`isomeric_smiles`）
- 可选列：`name` / `id` / `title`
- 每行一个结构；**点击时才生成 3D 坐标**，避免上千行卡死
- 失败行跳过并汇总提示，不阻断整批

**B. 原子坐标表**

```csv
element,x,y,z
O,0.0000,0.0000,0.0000
H,0.9572,0.0000,0.0000
H,-0.2390,0.9270,0.0000
```

- 必需列：`element`（或 `symbol`/`atom`）+ `x`/`y`/`z`
- 键由共价半径 + 最大价数推断；只适合小分子（≤ 1500 原子）
- 更稳妥的扩展：增加 `bonds.csv`（`i,j,order`），或直接要求上传 MOL/SDF

**C. 蛋白原子表（可选，二期）**

PDB 风格的 `record,atom_name,res_name,chain,res_seq,x,y,z` → 生成 PDB 文本 →
`Protein.from_pdb`。如果用户的 CSV 是这类，需要先确认列名。

## 4. 方案对比

| 维度 | A. Python 壳 + 原生窗口 | B. Web/WASM（+ Tauri） | C. Rust 原生自绘 UI | D. 3Dmol.js / Mol* |
| --- | --- | --- | --- | --- |
| UI 整合 | 中：查看器是独立窗口 | **高**：单页完全可控 | 高 | 高 |
| 开发速度 | 快（5–7 天） | 较快（13–16 天） | 中（10–14 天单窗口 / 6–9 天双窗口） | 最快（2–4 天） |
| 渲染性能 | 高（原生 GPU） | 中高（WebGL2） | 最高 | 中 |
| 部署 | 中：PyInstaller + 子进程二进制 | **高**：Electron 单文件（120–180 MB） | 高：单二进制 | 高 |
| 单文件/离线 | 中（onefile） | **高**（portable/AppImage/dmg） | 高（单二进制） | 中 |
| 依赖风险 | OpenGL 驱动、Python ABI | Chromium 自带，无系统依赖 | OpenGL 驱动、Rust 工具链 | 浏览器 |
| 大结构 | 好 | 受浏览器内存限制 | 最好 | 中 |
| 与参考库契合 | 高 | 高 | 最高 | 低（换库） |
| CSV/化学生态 | 好（pandas/RDKit） | 需 JS 自研 | 需 Rust 自研 | 需 JS 自研 |

### 推荐（按新约束修正）

1. **首选 B′：Electron + COSMol WASM**
   - 单窗口 UI：左侧结构列表 + 信息，中间画布，顶部打开/样式/截图。
   - 直接使用官方 npm 包，无需自己编译 Rust/WASM。
   - 三平台各产出一个单文件：`portable .exe`、`AppImage`、`.dmg`；所有资源内置，断网可用。
   - 代价：体积大（约 120–180 MB）、内存高；macOS 需要签名/公证。
2. **备选 Tauri + COSMol WASM**
   - 体积小（约 40–60 MB），但 Linux AppImage 仍依赖系统 WebKitGTK，Windows 需 WebView2；
     严格“单文件、零依赖”不成立，且 WebGL2 兼容性需实测。
3. **备选 Python**
   - 适合“脚本 + 查看器”工作流，或必须用 RDKit 做 2D 描述/聚类。
   - 缺点：`Viewer.show()` 是独立窗口；PyInstaller 单文件要带 `cosmol-viewer-native`
     子进程，打包复杂；原生 OpenGL 驱动差异。
4. **C 可行，但要分清两条路**
   - **R1 双窗口**：`NativeGuiViewer` 是公开 API，主窗口 + 独立 3D 子窗口；
     零改库、风险最低，约 6–9 人日，代价是两个窗口。
   - **R2 单窗口**：`Canvas` 本身就是 egui 控件（`custom_painting` / `update_scene` /
     `render_scene`），只需把 `mod shader` 改成 `pub mod shader` 暴露它；
     约 10–14 人日。详见 §11。
   - 不适合“重写渲染器”（wgpu/three-d）：卡通、表面、选择都要重做，4–6 周起。
5. **D 仅作为兜底/对标**
   - 3Dmol.js 对 SDF/PDB/mmCIF 支持成熟，两三天能出 demo；但等于放弃参考库，
     且蛋白卡通质量、后续扩展不如 COSMol。

## 5. 推荐方案设计（Electron + WASM）

### 5.1 分层

```
文件输入 / 拖拽
      ↓
格式识别（扩展名 + 内容嗅探）
      ↓
适配器：SDF 拆分 | PDB/mmCIF | CSV(A/B)
      ↓
结构模型 StructureEntry { id, name, kind, format, ck, meta, needsEmbed }
      ↓
场景管理（Scene / Style / 生命周期 free）
      ↓
COSMol WASM Viewer（canvas）
      ↓
UI：列表 / 信息 / 样式 / 截图 / 错误提示
```

### 5.2 模块清单

| 模块 | 职责 |
| --- | --- |
| `format-detect` | 扩展名 + magic 嗅探，给出 parser |
| `sdf` | 按 `$$$$` 拆分，逐条解析，取标题/属性 |
| `bio` | PDB/mmCIF → `Protein`；失败回退 `BioStructure.toMolecule`；HETATM 提取配体 |
| `csv` | 表头识别、列映射弹窗、SMILES 表、坐标表、键推断、逐行容错 |
| `scene` | 每个条目建 Scene，样式映射，recenter/scale，释放旧句柄 |
| `ui` | 打开/拖拽、列表、信息面板、样式切换、截图、CSV 模态框、进度/错误 |
| `electron/main` | 窗口、文件对话框、读文件、保存 PNG、`app://` 协议、网络封锁 |
| `worker`（二期） | 大 SDF/CSV 解析与 3D 嵌入移出主线程 |

### 5.3 渲染与生命周期

- `Viewer` 只创建一次，绑定固定 canvas；切换结构时 `viewer.render(newScene)`。
- 每个条目持有 `Molecule`/`Protein` 句柄；删除条目时 `free()`。
- Scene/Style 每次显示重建，渲染完成后释放上一份，避免 WASM 内存泄漏。
- SMILES 条目延迟 `embed3dConformer_()`；失败则提示该行不可用。
- 蛋白默认 `Cartoon().rainbowResidues()`；小分子默认 `BallAndStick()`。
- 截图用 `viewer.takeScreenshot()` 得到 PNG，经 IPC 调系统“保存文件”对话框。

### 5.5 CSV 列映射弹窗（本次新增需求）

触发：打开或拖入 `.csv` / `.tsv` 时，先读前几行，弹出映射对话框；用户确认后再导入。

```

│ 分隔符: [自动/逗号/分号/制表符]   首行表头 ☑    │
│                                                 │
│ 预览（前 5 行）                                 │
│ ┌──────┬─────────────────────────┬──────────┐  │
│ │ name │ SMILES                  │ MW       │  │
│ │ ...  │ ...                     │ ...      │  │
│ └──────┴─────────────────────────┴──────────┘  │
│                                                 │
│ 导入模式:  ◉ 每行一个分子（SMILES）             │
│            ○ 整表一个结构（坐标）               │
│                                                 │
│ SMILES 列: [SMILES ▾]    名称列: [name ▾]      │
│ 有效行: 1,236 / 1,240                           │
│                                                 │
│                       [取消]   [导入]           │
└─────────────────────────────────────────────────┘
```

- SMILES 列自动猜：表头匹配 `smiles` / `canonical_smiles` / `isomeric_smiles`；
  猜不中时必须由用户在下拉框中选择。
- 名称列可选（`name` / `id` / `title`），用于左侧列表显示。
- 坐标模式：选择 `element` / `x` / `y` / `z` 四列，并提示“键由距离推断，仅适合小分子”。
- 记忆：按表头签名记住上次映射（`localStorage`），下次自动带出。
- 批量：一次拖入多个 CSV 时，提供“应用到本次全部 CSV”。
- 有效行统计实时更新；“导入”按钮在有效行为 0 时禁用。
- 逐行容错：坏 SMILES 跳过，导入后汇总“成功 X 行 / 跳过 Y 行”。

### 5.6 Electron 桌面壳与离线打包

```
main process
├── BrowserWindow（contextIsolation=true, nodeIntegration=false）
├── app:// 自定义协议（从 asar 读 HTML/JS/WASM，避免 file:// 的 fetch 限制）
├── IPC：打开文件对话框 / 读取文本 / 保存 PNG
├── 网络封锁：拒绝所有非 app:// 请求
└── electron-builder：portable / AppImage / dmg

preload
└── contextBridge：openFiles(), readText(path), savePng(bytes)

renderer
├── 现有 Web UI（列表 / 画布 / 信息 / CSV 弹窗）
└── COSMol WASM + cosmolkit WASM（本地资源）
```

- 大文件：主进程 `fs.readFile` 读文本，经 IPC 传给渲染进程；超过阈值给进度/警告。
- 离线：不引入 CDN、不做自动更新；CSP 允许 `wasm-unsafe-eval`。
- 安全：禁用 `nodeIntegration`，只暴露必要 IPC，不加载远程 URL。
- 单文件产物：
  - Windows `portable` → 单个 `.exe`（自解压）；未签名会触发 SmartScreen 提示；
  - Linux `AppImage` → 单个文件；需要 FUSE，或加 `--appimage-extract-and-run`；
  - macOS `dmg` → 单个 `.dmg`，内含 `.app`；未签名需右键打开，正式分发建议
    Developer ID 签名 + 公证。
- 三平台构建：GitHub Actions matrix（windows / ubuntu / macos）或各平台机器分别构建；
  Electron 不支持从 Linux 交叉打 macOS 包。

## 11. Rust 原生方案补充评估

### 11.1 结论

**可行，而且比“必须改内核”的初判更乐观。** 渲染器本身已经是控件级的：
`crates/core/src/shader/canvas.rs` 里的 `Canvas` 提供

- `Canvas::new(gl, &Scene, logger)`
- `custom_painting(&mut egui::Ui)`：把 3D 画布画进任意 egui 区域
- `render_scene(&Scene)`：替换内容并重置相机
- `update_scene(&Scene)`：替换内容但保留当前相机（适合切样式）
- `play_animation(...)`、FPS/相机参数叠加

唯一障碍是 `lib.rs` 里 `mod shader;` 是私有的。把它改成 `pub mod shader;`
（或 `pub use shader::Canvas;`）即可在外部 crate 里直接使用 `Canvas`。
`Canvas` 的字段私有、方法公开，正好是“嵌入 widget”的形态。

因此有两条落地路径：

| 路径 | 形态 | 改参考库 | 工期 | 风险 |
| --- | --- | --- | --- | --- |
| **R1 双窗口** | 主窗口（列表/设置）+ `NativeGuiViewer` 独立 3D 窗口 | 无（公开 API） | 6–9 人日 | 低；两个窗口 |
| **R2 单窗口** | 自己的 eframe 窗口：左侧列表 + 中央 `Canvas` | 一行可见性补丁 | 10–14 人日 | 中；OpenGL、补丁维护 |
| R3 重写渲染 | wgpu/three-d 自绘卡通/表面 | 完全自研 | 4–6 周+ | 高，不建议 |

### 11.2 R1：双窗口（零改库）

```rust
cosmol_viewer_core::register_render();          // 必须在 main 开头
let viewer = Viewer::show(&scene, 900.0, 700.0)?; // 启动 current_exe --child
viewer.update(&new_scene);                       // 切换结构
let png = viewer.take_screenshot()?;             // 截图
```

- 同一个可执行文件既是主程序又是渲染子进程（`--child` 参数）。
- `NativeGuiViewer` 用 `Drop` 管理子进程，主程序退出时自动清理。
- 主窗口用 eframe/egui 做文件列表、CSV 弹窗、样式切换；3D 窗口可拖拽旋转/缩放。
- 代价：两个窗口。可以把控制面板做窄、置顶，放在 3D 窗口旁边，但无法真正合并。
- 适合“先做出来、快速验证”的版本，风险最低。

### 11.3 R2：单窗口内嵌 Canvas

```rust
// 参考库补丁（cosmol_viewer_core/src/lib.rs）
pub mod shader;   // 原为 mod shader;

// 应用侧
struct MolVisionApp {
    canvas: cosmol_viewer_core::shader::Canvas<RustLogger>,
    entries: Vec<Entry>,
    ...
}

impl eframe::App for MolVisionApp {
    fn update(&mut self, ctx: &egui::Context, _frame: &mut eframe::Frame) {
        egui::SidePanel::left("list").show(ctx, |ui| self.sidebar(ui));
        egui::CentralPanel::default().show(ctx, |ui| {
            self.canvas.custom_painting(ui);
        });
    }
}
```

- 初始化：`eframe::run_native(..., Renderer::Glow, ...)`，在 `CreationContext` 里
  `cc.gl.clone().unwrap()` 得到 `Arc<glow::Context>`，再 `Canvas::new(...)`。
- 切换结构：`canvas.render_scene(&scene)`；只换样式：`canvas.update_scene(&scene)`。
- 重置视角：重新 `render_scene`（会从 scene 恢复相机）。
- 文件打开：`rfd` 原生对话框，或纯 egui 的 `egui-file-dialog`（避免 Linux GTK 依赖）；
  拖拽用 `ctx.input(|i| i.raw.dropped_files.clone())`。
- CSV 弹窗：egui `Window` + `ComboBox` + `egui_extras::TableBuilder` 预览。
- 截图：用 egui 的 `ViewportCommand::Screenshot` 截当前画布（与 `App` 内部做法一致），
  或 `ImageRenderer::save_png` 离屏导出。
- 解析：直接用 `cosmolkit` Rust crate，和 Python 侧同源。

### 11.4 必须提前正视的风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| OpenGL 驱动 | eframe/glow 需要 OpenGL 3.3+；没有 Chromium 的 SwiftShader 软件兜底。远程桌面、虚拟机、老驱动可能打不开 | 启动时检测 GL 版本并给明确提示；文档列最低要求；必要时提供“离屏截图模式” |
| 中文字体 | egui 默认字体不含 CJK，界面会显示方框 | 内置 Noto Sans SC 子集（约 2–5 MB）；或运行时加载系统中文字体 |
| 参考库补丁 | R2 依赖 `Canvas` 这一层内部 API，0.6.x 升级可能变 | 锁 0.6.2；把补丁做成独立 patch 文件；升级时只跑适配层回归 |
| 单文件边界 | Windows 可单 exe；Linux 仍依赖 libX11/libGL/glibc，通常用 AppImage；macOS 是 `.app`/`.dmg` | 与 Electron 相同：按平台产出单一**下载文件**，不承诺“零动态库” |
| 跨平台构建 | macOS 包不能在 Linux 交叉构建；三平台要分别构建 | GitHub Actions matrix 或三台机器 |
| 文件对话框 | `rfd` 在 Linux 走 GTK/XDG portal，增加依赖 | 用 `egui-file-dialog`，或同时支持拖拽 + 路径输入 |
| 验证环境 | 本沙箱 X11 GLX 不可用，无法跑原生窗口 | 需在真实桌面做一次冒烟测试；先编译 + 离屏渲染验证 |

### 11.5 与 Electron 的取舍

| 维度 | Rust R2 | Electron |
| --- | --- | --- |
| 安装包 | 约 20–50 MB（含字体/资源） | 约 120–180 MB |
| 内存 | 低 | 高（Chromium） |
| 渲染兼容性 | 依赖系统 OpenGL | 自带 ANGLE/SwiftShader，兼容性更好 |
| 启动速度 | 快 | 较慢 |
| UI 开发效率 | 中（egui） | 高（HTML/CSS） |
| 单窗口体验 | 好 | 好 |
| 维护成本 | 需维护参考库补丁 | 无补丁，跟随 npm 包 |
| 三平台一致性 | 需逐平台验证 GL/字体/对话框 | 高 |

**建议**：如果“体积小、原生性能”是硬指标，选 **R2**；如果“拿到就能在任意
Windows/Linux/macOS 机器上跑”是硬指标，选 **Electron**。R1 适合先做可用原型，
后续再决定是否投入 R2 合并窗口。

## 12. PySide6 + PyOpenGL + RDKit 评估（放弃 COSMol）

### 12.1 结论

**技术上可行，但“简易”要看蛋白卡通是不是硬要求。**

| 范围 | 工期（1 名熟练开发） | 说明 |
| --- | --- | --- |
| 小分子 + PDB 球棍/棍状 | **5–7 周** | RDKit 解析 + PySide6 UI + PyOpenGL 球/棍渲染 |
| 再加蛋白卡通 | **10–14 周** | 需要二级结构、CA 样条、 ribbon 网格、着色 |
| 再加表面/测量/选择 | +4–8 周 | 表面（SES/SAS）尤其耗时 |

对比：COSMol 路线 Rust R1 6–9 人日、R2 10–14 人日、Electron 13–16 人日。
放弃 COSMol 的代价主要不是解析，而是**重新实现渲染器**。

### 12.2 各库覆盖什么

| 能力 | 负责 | 说明 |
| --- | --- | --- |
| 桌面 UI、文件对话框、表格、拖拽 | PySide6 | 成熟；LGPLv3，需合规确认 |
| SDF / SMILES / 2D 描绘 / 3D 构象 / 描述符 | RDKit | 强项；`EmbedMolecule` 生成 3D |
| PDB 原子/键/残基/链 | RDKit `MolFromPDBFile` | 能读，但不是蛋白结构库；无二级结构 |
| mmCIF | Biopython | RDKit 不直接支持 mmCIF |
| 球/棍/卡通/表面渲染 | **自研** | PyOpenGL 只是 GL 绑定，不含分子表示 |

RDKit 实测（`sanitize=False, removeHs=False`）：

- 1CRN：327 原子 / 337 键，链 A
- 1M17：2,546 原子 / 2,581 键（含 HETATM）
- 1BNA：566 原子 / 544 键，链 A/B
- 阿司匹林 SMILES：13 原子、1 个 3D 构象、C9H8O4 / 180.16、2D 描绘正常

结论：**解析层够用**；缺的是二级结构、卡通几何、表面、选择、相机交互。

### 12.3 自研清单（PyOpenGL）

| 模块 | 工期 | 备注 |
| --- | --- | --- |
| 球/棍渲染（instancing、CPK 配色、双/三键偏移） | 2–3 周 | GL 3.3 core + GLSL |
| 相机（arcball）、拾取、深度/MSAA | 1 周 | 颜色 ID 拾取最简单 |
| 蛋白卡通（DSSP/pydssp + CA 样条 + ribbon 网格） | 4–6 周 | 质量通常低于 COSMol |
| PySide6 主界面 + 列表 + 信息 + CSV 弹窗 | 2 周 | 可复用前文 CSV 设计 |
| 打包/CI（三平台） | 1–2 周 | PyInstaller/Nuitka |

### 12.4 更省力的替代（仍可保留 PySide6 + RDKit）

1. **VTK / PyVista**：`vtkMoleculeMapper` 做球棍，`vtkProteinRibbonFilter` 做卡通，
   `QVTKRenderWindowInteractor` 嵌 Qt。省掉 shader 和卡通自研，约 **6–9 周**；
   包体大（VTK 100–200 MB），卡通质量是基础级，需实测。
2. **QWebEngineView + 3Dmol.js / NGL**：3D 渲染现成，卡通/表面/标签都有，约 **5–7 周**；
   但 QtWebEngine 本质是 Chromium（约 150 MB），包体不比 Electron 小。
3. **COSMol 子窗口 + PySide6 主界面**：3D 质量最好，6–9 人日；代价是两个窗口，
   不算“完全放弃 COSMol”。

### 12.5 打包与体积

- PySide6 + RDKit + numpy + PyOpenGL 的 PyInstaller `--onefile` 约 **150–300 MB**，
  和 Electron 同量级甚至更大；**并不会因为换 Python 就变小**。
- onefile 启动要解压到临时目录，首启慢；杀软误报概率高于原生/Electron。
- macOS 需要 `.app`/`.dmg`；Linux 仍依赖系统 libGL/X11，通常用 AppImage；
  Windows 单 exe 可行。
- Qt6 的 OpenGL 在 macOS 上可用但已弃用；Windows/Linux 需要显卡驱动。
- PySide6 是 LGPLv3：动态链接、允许替换 Qt 库；闭源商用需法务确认，
  或改用 PyQt6（GPL/商业许可）。

### 12.6 建议

- **蛋白卡通是硬要求**：不要用 PyOpenGL 从头写卡通。优先 VTK/PyVista 或
  QWebEngine + 3Dmol.js；或者保留 COSMol 只做渲染。
- **化学功能为主（SMILES/2D/描述符/构象），卡通次要**：PySide6 + RDKit + PyOpenGL
  是合理组合，5–7 周可做出小分子 + 蛋白棍状查看器。
- **体积优先**：PySide6 方案不占优；Rust R2（20–50 MB）更小。
- **工期优先**：COSMol R1/R2 或 Electron 仍快一个数量级。

## 13. 新增需求影响评估：2D / 标签 / 距离 / 批量

### 13.1 新增需求

1. **2D 结构式必须**
2. **批量出图必须**

### 13.2 与 COSMol 的能力冲突

COSMol 的公开 API 擅长“渲染”，但不提供“标注”：

| 需求 | COSMol 现状 | 结论 |
| --- | --- | --- |
| 文本标签 | 没有 text/label 图元，只有 Sphere/Stick | 需自研覆盖层或改内核 |
| 原子/残基拾取 | 没有 picking API | 需自研（投影 + 最近邻） |
| 距离标注 | 没有测量 API | 需自研线段 + 标签 |
| 读取当前相机 | `setCameraView` 只能写；`Scene.toJson()` 是场景相机，不是拖拽后的实时相机 | 需改 WASM 暴露相机 |
| 截图包含标注 | `takeScreenshot()` 只截 WebGL 画布，HTML/SVG 覆盖层不会进图 | 需二次合成 |
| 2D 结构式 | 有 `coordinates2d()`，但布局/立体化学/投稿级质量不如 RDKit | 建议 RDKit WASM |

补充：`cameraParameterLogging(true)` 会以约 5 Hz 输出
`camera: azimuth=..., elevation=..., distance=..., target=[...], fov=...`，
可以在控制台拦截并解析，但延迟明显、依赖日志格式，只适合做原型，不适合产品。

### 13.3 三条路线

| 路线 | 3D 渲染器 | 标签/测量 | 截图含标注 | 卡通质量 | 预计工期 |
| --- | --- | --- | --- | --- | --- |
| **A（推荐）** | **3Dmol.js** | 原生 `addLabel` / `addLine` / `addCylinder` / `setClickable` | ✅ 图元在场景内，`pngURI` 直接包含 | 中 | 5–7 周 |
| B | COSMol + 补丁/覆盖层 | 需暴露相机 + HTML/SVG 覆盖 + 导出合成 | ❌ 需额外合成 | **高** | 8–10 周 |
| C | Mol* | 内置测量/标签，投稿级 | ✅ | **高** | 6–9 周，集成更重 |

**3Dmol.js 的关键能力**（已核对 2.5.5 API）：

- 解析：PDB、mmCIF、SDF、MOL2、XYZ；自带二级结构计算与 cartoon
- `addLabel(text, {position, fontSize, backgroundColor, inFront})`
- `addLine` / `addCylinder` / `addArrow`：距离标注的线和箭头
- `setClickable({}, true, cb)`：点原子回调，用于选两点测距
- `getView()` / `setView()`：相机可读写，方便固定视角出图
- `pngURI()`：截图包含 labels/shapes；配合 `setWidth/setHeight` 做高分辨率
- 体积小（构建后约 1–2 MB），BSD 许可，完全离线

### 13.4 2D：RDKit WASM

“放弃 RDKit”指的是 Python 版；2D 结构式建议用 **`@rdkit/rdkit`（WASM）**：

- `get_mol(molblock/smiles)` → `get_svg(width, height)` / `draw_to_canvas`
- 支持立体化学、电荷、芳香环、原子标签；SVG 可直接进论文
- 体积约 7.5 MB；纯 JS/WASM，不需要 Python 运行时
- PDB 全蛋白不做 2D；配体/小分子可 2D

### 13.5 批量出图

- 3D：逐条建场景/相机 → 目标分辨率 → `pngURI` → 收集
- 2D：逐条 `get_svg`，可选 PNG（canvas 栅格化）
- ZIP 打包（JSZip）+ 清单 CSV（文件名、SMILES、原子数、来源）
- 进度条、取消、失败项汇总
- 命名模板：`{name}_{index}_{style}.png`

### 13.6 修正后的工期

| 阶段 | 人日 |
| --- | --- |
| Electron 壳 + 文件/列表/样式 + CSV 列映射 | 10–13 |
| 3Dmol 接入（SDF/PDB/mmCIF、cartoon、相机、截图） | 5–7 |
| 2D RDKit WASM（查看 + SVG/PNG 导出） | 4–6 |
| 标签/距离标注（含拾取、连线、标签布局） | 5–7 |
| 批量出图（3D+2D、ZIP、进度） | 3–4 |
| 打包/CI/离线验证/文档 | 4–6 |
| **合计** | **31–43 人日（约 6–9 周）** |

如果坚持 COSMol 路线（补丁 + 覆盖层 + 合成），在上述基础上再 **+2–3 周**，且需维护
WASM 补丁。

### 13.7 建议

1. **3D 渲染器改为 3Dmol.js**，2D 用 RDKit WASM；这是唯一能在合理工期内同时满足
   “查看 + 标签 + 测距 + 批量出图”的组合。
2. COSMol 的卡通质量更好，但它的 API 不面向“标注出图”；如果卡通质量是硬指标，
   走路线 B，预算 8–10 周，并接受补丁维护。
3. Mol* 作为“高质量 + 内置测量”的备选，若 3Dmol 的卡通质量不能满足，再评估。

> 这一步会改变已锁定的“COSMol 3D”决策，需要明确确认后再进入开发。

## 14. COSMol 功能增强方案（保留 3D 渲染器）

### 14.1 结论

**可以增强，但需要动一次 COSMol 的 Rust/WASM 层，外加一层 JS 标注系统。**
纯前端“加个弹窗”不够，因为 COSMol 不暴露相机、拾取和文本图元；截图也只含 WebGL 画布。

### 14.2 需要补的三件事

| 缺口 | 补法 | 工作量 |
| --- | --- | --- |
| 读取实时相机 | 给 `Canvas` 增加 `camera_state()`，`App` 处理 `GetCamera` 请求，WASM 导出 `viewer.cameraState()` | 3–5 人日（含 WASM 构建） |
| 标签/测距绘制 | 在 3D 画布上叠一张透明 `<canvas>`，用 2D API 画文字/线；与 COSMol 相机同步 | 6–9 人日 |
| 导出含标注 | 3D 截图 + 标注画布按目标分辨率重绘，合成为最终 PNG | 4–5 人日 |

> 备选（不推荐）：用 `cameraParameterLogging` 的日志解析相机。约 5 Hz、依赖日志格式，
> 只适合原型。

### 14.3 推荐架构

```
┌────────────────────────────────────────────┐
│ COSMol WASM（3D 画布）                     │
│  + viewer.cameraState() 补丁               │
└───────────────┬────────────────────────────┘
                │ 相机参数（azimuth/elevation/roll/distance/target/fov）
┌───────────────▼────────────────────────────┐
│ 透明 2D annotation canvas                  │
│  - 3D→屏幕投影                              │
│  - 原子/残基标签                            │
│  - 距离线 + 距离文字                        │
│  - 点击拾取（投影最近邻）                   │
└───────────────┬────────────────────────────┘
                │ 同一套 draw(ctx, scale)
┌───────────────▼────────────────────────────┐
│ 导出合成器                                  │
│  3D PNG（目标分辨率）+ 标注重绘 → 最终 PNG  │
└────────────────────────────────────────────┘

RDKit WASM（2D）：独立视图 / SVG / PNG
```

要点：**标注只画一次逻辑，显示和导出共用**。透明 canvas 用 `pointer-events:none`，
点击监听挂在容器上，用“按下/抬起位移 < 4px”区分点击与拖拽。

### 14.4 标签与测距的交互

**标签（指定原子或残基，不是全量）**

- 分子：点击原子 → 加入标签；蛋白：点击残基（默认取 CA）→ 加入标签。
- 标签模板：
  - 原子：`元素 + 原子名`（如 `O1`、`CA`）
  - 残基：`链 + 序号 + 残基名`（如 `A:123 ASP`）
- 右侧“标注列表”可删除、隐藏、改颜色/字号；标签可加引线，避免压住结构。
- 简单避让：默认偏移 (8,-8)，重叠时按序号错开；手动拖拽放二期。

**距离标注（多条持久、可删除）**

- 点击原子 A → 点击原子 B → 生成 `dashed line + "3.2 Å"`。
- 数据结构：`{aAtomId, bAtomId, distance, color, dash}`；保存在条目的标注集合里。
- 列表支持删除单条/全部；相机旋转、样式切换、批量导出时都保留。
- 线的端点可加小圆点；标签放在中点上方，避免与原子标签重叠。

### 14.5 拾取与投影

- 加载时建立 `pickables`：
  - 分子：`coordinates3d` + 元素 + 原子索引
  - 蛋白：`protein.atoms` 的 `position`、`name`、`residue`（残基标签取 CA）
- 点击时把所有点用当前相机投影到屏幕，取 10 px 内最近者；50k 原子一次投影可接受。
- 投影公式与 COSMol `CameraState::matrices` 一致：orbit 四元数 → view，
  `perspective(fov, aspect, 0.1, 2000)` → clip，再转屏幕坐标。
- 必须处理 `devicePixelRatio`、canvas CSS 尺寸与 backing size 的比例。

### 14.6 导出与批量

- 单张：把 3D 画布按目标分辨率重渲染 → `takeScreenshot()` → 画到 2D 合成 canvas →
  用同一 `drawAnnotations(ctx, scale)` 重绘标签/测距 → 导出 PNG。
- 批量：逐条设置相机（固定视角预设）→ 渲染 → 合成 → 收集；JSZip 打包 + 清单 CSV。
- 2D：RDKit WASM `get_svg(w,h)` 导出 SVG，或 `draw_to_canvas` 出 PNG；
  与 3D 一起打包。
- 透明底：先验证 WASM 截图 alpha；不行则白底/深底二选一，或后期加离屏通道。

### 14.7 2D 结构式（RDKit WASM）

- `@rdkit/rdkit`：`get_mol()` → `get_svg(width,height)` / `draw_to_canvas`。
- 小分子/配体支持；全蛋白不做 2D。
- SVG 是矢量，适合论文；PNG 用于批量预览。

### 14.8 工期（在 Electron + COSMol 基线上）

| 工作 | 人日 |
| --- | --- |
| WASM 构建 + 相机补丁 | 5–7 |
| 标注画布（投影/标签/测距/拾取） | 8–11 |
| 导出合成 + 批量 | 5–7 |
| RDKit WASM 2D（视图 + SVG/PNG） | 4–6 |
| Electron 壳 + 列表/样式 + CSV 列映射 | 10–13 |
| 打包/CI/离线验证/文档 | 5–7 |
| **合计** | **37–51 人日（约 8–10 周）** |

两人并行（Rust/WASM 补丁 + 前端标注/UI）可压到约 **5–7 周**。

### 14.9 风险

| 风险 | 对策 |
| --- | --- |
| WASM 补丁维护 | 锁 0.6.2；补丁独立成 patch；尽量上游 PR（相机 getter 是通用需求） |
| 投影与 COSMol 不一致 | 用同一相机参数 + 单元测试对比若干已知点 |
| 标注与截图对不齐 | 显示/导出共用 `drawAnnotations`，按比例缩放 |
| 标签重叠 | 默认偏移 + 简单避让；手动拖拽二期 |
| 大结构拾取慢 | 只投影一次点击；必要时按视锥裁剪 |
| 透明背景 | 先实测 alpha；不行则白底方案 |
| 2D 质量 | RDKit 是成熟方案；先做小分子/配体 |

### 14.10 建议

1. **保留 COSMol 3D**，做“相机 getter 补丁 + 透明标注 canvas + 导出合成”。
2. **2D 用 RDKit WASM**，与 3D 并列，不做 Python。
3. 先做 **单条标注 + 单张导出** 打通链路，再做批量与标签避让。
4. 相机补丁尽量提 PR 给上游；即使不合并，补丁面很小，可控。
